# Askora 文档索引

`docs/` 保存 Askora 的产品设计、教学内核设计及其研究依据。

当前文档体系遵循一个基本原则：**研究依据、正式设计与实际实现必须区分，避免多份文档同时被误认为“最终答案”。**

## 1. 当前目录

```text
docs/
├── README.md
└── design/
    ├── 个人AI辅助学习平台设计方案.md
    ├── AI学习系统算法与教学内核设计.md
    └── research/
        ├── README.md
        ├── evidence/
        └── synthesis/
```

## 2. 主设计文档

### [`design/个人AI辅助学习平台设计方案.md`](design/个人AI辅助学习平台设计方案.md)

Askora 的产品、技术架构与阶段执行基线，负责回答：

- Askora 要做成什么产品；
- 系统整体由哪些模块组成；
- 数据、服务、交互与工程边界如何设计；
- 当前阶段应优先实现什么。

其中的目标态设计不等于代码已经实现。

### [`design/AI学习系统算法与教学内核设计.md`](design/AI学习系统算法与教学内核设计.md)

Askora 学习科学、算法与教学内核的正式设计基线，负责回答：

- 如何判断用户真正掌握了什么；
- 如何进行评估、错误诊断与学习者建模；
- 如何选择教学策略、安排学习路径和复习；
- RAG、知识图谱、LLM、Agent、Bandit/RL 等技术分别承担什么职责；
- “AI 学习工具的八类技术系统”如何划分职责、状态和决策所有权。

对于教学内核及八类技术系统的正式定义，以该文档为准。

## 3. Research 研究资产

[`design/research/`](design/research/) 保存“为什么这样设计”的研究依据和设计推导，不作为第二套正式规范。

其内部采用两层结构：

```text
research/
├── evidence/    # Deep Research、论文、行业实践等证据
└── synthesis/   # 跨证据综合、架构推导、分系统设计研究
```

### `evidence/`

用于保存教育科学、ITS、学习者建模、检索与知识架构、教学策略、记忆调度、LLM/Agent 治理等 Deep Research 证据。

此层允许与正式设计存在内容重复，因为其核心价值是：**证据来源、论证过程、边界条件和反例可追溯。**

### `synthesis/`

用于保存从研究证据进一步形成的 Askora 架构推导，包括：

- 八类技术系统现状诊断；
- 公共架构冻结稿；
- 4.1～4.8 八个技术系统各自的系统设计研究稿；
- Deep Research 原始研究的综合与溯源。

原先因上下文规模而生成的“批次 1～4”文件已经按真实系统边界拆分为 4.1～4.8 八份独立研究稿，不再使用批次命名。

详细治理规则见 [`design/research/README.md`](design/research/README.md)。

## 4. 文档权威性

文档关系按以下顺序理解：

```text
Evidence
   ↓
Synthesis
   ↓
Canonical Design
   ↓
Implementation
```

具体规则：

1. `research/evidence/` 保存证据，不直接定义产品接口或实现契约；
2. `research/synthesis/` 保存研究推导，不与正式设计并列成为第二套规范；
3. 产品整体设计以 `个人AI辅助学习平台设计方案.md` 为阶段执行基线；
4. 教学算法、学习科学和八类技术系统以 `AI学习系统算法与教学内核设计.md` 为正式设计基线；
5. 若研究稿与正式设计冲突，以正式设计为准；
6. 若设计文档与当前代码实际行为不一致，判断“已经实现了什么”时，以代码、配置、数据库迁移和可执行测试为准，并随后修正文档。

## 5. 后续文档治理

新增设计研究时统一遵循：

```text
Deep Research / 外部证据
→ 保存到 research/evidence
→ 跨证据推导保存到 research/synthesis
→ 被采纳的结论回写主设计文档
→ 实现后由代码与测试验证
```

禁止长期保留 `批次1`、`阶段2`、`最终版2` 等执行过程命名。正式文档应按其真实产品、系统或知识边界命名。
