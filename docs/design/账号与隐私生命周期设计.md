# Askora 账号与隐私生命周期设计

> 状态：Canonical Design
> 授权：用户于 2026-08-09 采纳 P1-05 推荐方案，并授权以真正关闭 P1-05、通过相关测试为目标完成治理与实现
> 直接实现合同：`docs/specs/platform/identity-privacy-lifecycle.md`

## 1. 目标与产品边界

Askora 是私人、本地优先的个人学习 App。账号能力的首要目标不是构建公开 SaaS 身份平台，而是让用户能可靠地：

- 修改密码并知道哪些会话仍然有效；
- 查看和撤销当前 App 实例或其他已登录实例；
- 在没有短信、邮件帮助台或第三方身份服务时使用离线恢复套件恢复账号；
- 明确区分退出、撤销会话、删除全部学习数据和删除账号；
- 在高风险删除前看到精确范围，在删除后取得不含个人内容的完成证明；
- 防止待处理任务、projection rebuild 或 App 管理的旧备份静默恢复已删除数据。

P1-05 不引入短信/邮件供应商、社交登录、MFA、组织账号、儿童/监护人新流程或公网多租户运营能力。这些能力若未来需要，必须另行治理。

## 2. 当前问题

当前 access/refresh JWT 没有 durable session family；Redis/进程内集合只保存短期撤销状态。退出只吊销当前 access JTI，无法可靠撤销对应 refresh token。`UserStatus.DELETED` 也只有软删除枚举，没有跨数据库、文件、ledger、outbox 和 projection 的删除闭环。

部分记录直接带 `user_id` 或 `pseudonym_id`，另一些只通过 goal、plan、activity、session、decision 或 JSON reference 间接关联用户。直接级联删除 `users` 行既会漏数据，也会绕过 SYS01～SYS08 的唯一写入边界。

## 3. 目标架构

Identity & Privacy 是平台横切边界，不是第九个学习领域系统：

```text
Platform Identity
  owns UserAccount credential state / AuthSession / RecoveryCredential

Platform Privacy Coordinator
  owns deletion request / subject manifest / step receipt / audit tombstone
  sends owner-scoped erasure commands

SYS01..SYS08 owner erasure handlers
  erase only records/files/projections owned by that system
  return deterministic receipts
```

Privacy Coordinator 不取得 Knowledge、LearnerState、Assessment、TeachingAction、Plan、ReviewSchedule 或 Execution truth 的普通写权限。隐私删除是 `STATE-023` / `EVENT-071` 明确允许的特殊治理路径；普通业务代码仍不得修改或删除 immutable ledger。

## 4. 身份与会话

`AuthSession` 是会话的 durable truth，SQLite 与 PostgreSQL 语义一致。每次登录创建一个 session/token family；access 与 refresh token 都携带 exact `session_id`、token-family id 和 credential version。每个受保护请求必须同时验证：

```text
JWT signature/type/expiry
+ UserAccount ACTIVE
+ token credential_version == current credential_version
+ AuthSession ACTIVE and not expired
+ device/app-instance binding when configured
```

Redis 只能缓存 session/revocation 查询。Redis 丢失、重启或不可用不得让已撤销会话重新生效。

Refresh rotation 必须在数据库内原子消费当前 refresh JTI 并写入新 JTI。已消费 refresh token 再次出现表示可能重放，必须撤销整个 token family并要求重新登录。

## 5. 密码与恢复

新密码使用版本化 password policy。新建或修改的密码使用 Argon2id；历史 bcrypt hash 继续验证，并在成功认证时渐进 rehash，不要求批量明文迁移。修改密码与账号恢复都会递增 credential version、撤销既有 session family，并生成新会话或要求重新登录。

本地恢复套件使用高熵随机 secret：

- secret 只在创建或成功恢复后展示一次；
- 服务端只保存 keyed digest，不保存明文；
- secret 单次使用，使用后立即轮换；
- 验证失败有 durable throttling 和稳定、不枚举账号的错误；
- 不使用安全问题；首版不发送短信或邮件。

注册时自动生成首份恢复套件；既有账号可在设置中通过当前密码创建或轮换。

## 6. 删除语义

四个用户动作必须保持不同合同：

| 动作 | 身份 | 学习数据 | 会话 |
|---|---|---|---|
| 退出当前实例 | 保留 | 保留 | 撤销当前 token family |
| 撤销指定实例 | 保留 | 保留 | 撤销指定 token family |
| 删除全部学习数据 | 保留 | 删除 | 当前账号继续可用 |
| 删除账号 | 删除/去标识化 | 全部删除 | 全部撤销 |

账号删除使用：

```text
ACTIVE
→ DELETION_PENDING
→ PURGING
→ DELETED

DELETION_PENDING → ACTIVE      (cancel)
PURGING → DELETION_BLOCKED     (permanent reconciliation failure)
DELETION_BLOCKED → PURGING     (explicit retry/repair)
```

创建删除请求前先生成 versioned preview，包含数据库记录、原始文件、projection、pending task、model execution/audit record 和排除项计数。请求必须携带 preview version、policy version、幂等键、当前密码和显式确认短语。

进入 `DELETION_PENDING` 后立即撤销普通会话并停止新业务写入；发起实例只取得短期、单用途 deletion-control token，可查看状态或在冷静期内取消。默认冷静期由版本化策略定义，首版为 24 小时；测试可通过依赖注入时钟和测试策略立即到期，生产语义不由前端时间决定。

## 7. Subject Manifest 与删除编排

删除 preview 必须生成 durable subject manifest。直接 user scope、pseudonym scope、稳定 owner reference 和 JSON reference 通过显式 registry 解析；不得以“本机只有一个用户”作为归属证据。无法唯一归属的记录进入 blocking issue，账号不得被标记删除完成。

删除步骤按 owner 串行、可重试、幂等执行：

1. Identity 冻结账号、撤销 sessions/recovery credential；
2. SYS08 取消该用户未完成的 outbox/workflow；
3. SYS01 删除私人原始文件、内容事实和其私人 projection；
4. SYS02 删除 retrieval projection/cache；
5. SYS03～SYS07 删除各自 owner state/version/evidence；
6. SYS08 删除 transcript、model execution、event/decision/outcome records；
7. 重建幸存 projection，并执行 manifest/reconciliation 零残留检查；
8. Identity 清除 PII/password/credential，写不含内容的 tombstone 与 restore barrier。

每一步单独提交 receipt；进程退出后从未完成步骤恢复。普通 immutable listener 可继续拒绝删除，owner erasure repository 使用明确的 privacy-only Core deletion path，并仅接受已冻结 manifest。

## 8. 恢复屏障

账号删除完成后写入数据库外的本地 restore barrier。App 管理的数据库恢复或旧快照启动必须在认证前检查 barrier；匹配已删除 subject 的旧账号不得登录，也不得被后台任务继续处理。首版在检测到旧快照时 fail closed 并重新执行隐私清除；手工替换整个 App 数据目录属于产品无法保证的外部边界，必须在删除结果中明确说明。

## 9. 验证与发布声明

关闭 P1-05 必须覆盖 contract、migration、SQLite/PostgreSQL、并发、重启、Redis 故障、refresh replay、恢复限流、cross-user、文件删除、projection rebuild、旧备份屏障、真实浏览器与可访问性。

该工作可形成 Engineering 与 Policy/Ownership 结论；它不涉及教学效果，不能产生真人学习效果声明。Learning Evidence 继续与账号可靠性分开。
