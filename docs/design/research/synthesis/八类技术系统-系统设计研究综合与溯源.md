## 1. 文档目的

本文件用于保存“八类技术系统”Deep Research 分系统设计阶段的研究 provenance，而不是再复制一份与正式设计高度重复的全文。

此前为了控制单次研究任务规模，系统设计阶段被拆成四个执行批次，每批覆盖两个技术系统。四个批次均为高价值 Deep Research 中间成果，但“批次”只是执行边界，不是 Askora 的知识或架构边界。

因此当前治理方式为：

1. 研究证据继续保存在 `../evidence/`；
2. 公共架构与现状诊断保存在本目录；
3. 四个批次设计结论已吸收到正式设计文档；
4. 删除工作区中的四个批次文件，避免出现第二套可被误认为权威设计的全文；
5. 原始内容通过 Git commit 与 blob SHA 永久可追溯。

## 3. 四个批次形成的核心系统边界

### 3.1 内容解析与知识建模

核心职责：把不可信原始材料转换为可版本化、可定位原文、可审核、可供教学和评估使用的规范知识模型。

关键所有权：知识对象、概念、关系与来源事实是否发布。

### 3.2 检索与知识供给

核心职责：根据既定 TeachingAction 和暴露约束，生成本轮可引用的 `EvidenceBundle`。

关键所有权：哪些候选证据进入当前 EvidenceBundle。

### 3.3 学习者建模

核心职责：把多次行为和评估证据融合为带不确定性的 `LearnerState` 与 `MasteryEstimate`。

关键所有权：长期学习者状态估计，而不是单次作答判分。

### 3.4 评估与错误诊断

核心职责：对单次 Attempt 进行可复现测量，发布 `AssessmentResult`、错误类型和误区证据。

关键所有权：单次测量与诊断，不直接宣布长期掌握。

### 3.5 教学策略选择

核心职责：在当前 LearningObjective 已确定的情况下决定“当前怎么教”。

关键所有权：`TeachingAction`、提示强度、支架等级和答案暴露上限。

### 3.6 学习路径与任务调度

核心职责：在目标、前置图、LearnerState、ReviewSchedule 和现实时间约束下决定“下一步学什么”。

关键所有权：`LearningPlan`、`LearningObjective` 和日任务优先级。

### 3.7 记忆保持与复习调度

核心职责：依据有效提取证据和记忆模型计算遗忘风险与下一建议复习时间。

关键所有权：`ReviewSchedule`、`next_due_at`，不替代完整 mastery 判断。

### 3.8 LLM 生成、Agent 编排与可信控制

核心职责：把前七个领域系统已经确定的状态、证据和教学决策可靠执行为用户交互。

关键所有权：模型/工具执行路径与工程降级；LLM/Agent 不拥有业务真相。

## 4. 研究结论的正式落点

四个批次形成的结论已经进入 `docs/design/AI学习系统算法与教学内核设计.md` 第 4 章，包括但不限于：

- 八类系统的唯一核心职责；
- 决策与状态唯一所有者；
- 统一领域对象；
- 系统上下游边界；
- 教学证据、长期状态、即时动作、学习计划和复习调度之间的分离；
- LLM/Agent 不直接拥有学习者状态、教学策略与计划的治理原则；
- 算法从规则、启发式、监督学习到 Bandit/RL 的渐进采用原则。

正式设计发生演进时，只修改 Canonical Design；本文件仅在研究 provenance、研究结论状态或历史来源发生变化时更新。

## 5. 后续研究规则

新的 Deep Research 若继续扩展八类技术系统：

- 新论文、新实验、新行业证据 → 写入 `evidence/`；
- 跨证据形成的新架构推断 → 写入 `synthesis/`；
- 被正式采纳的系统定义、接口、算法与约束 → 回写 Canonical Design；
- 仅为解决上下文长度而产生的“批次文件” → 完成整合后删除，Git 历史负责保留过程。

这样保证研究资料可以充分保留，同时避免 `research/` 与正式设计同时存在多套“最终答案”。
