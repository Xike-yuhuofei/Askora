# Askora v0.3 候选范围分析

> 状态：Historical Pre-Design / Scope Analysis — COMPLETED
> 日期：2026-08-07  
> 基线：v0.2 First Vertical Learning Loop（FROZEN）  
> 目的：记录 v0.3 主线形成前的范围选择；其结论已进入后续 Research Synthesis、Canonical Design、ADR 与 Specs，不代表当前项目状态。

## 1. 决策原则

v0.3 不从零重构 Askora，而只对 v0.2 冻结基线做增量设计。

优先级按以下标准判断：

1. 是否直接提升 Askora 相对普通 RAG/聊天 Tutor 的核心差异；
2. 是否能让 v0.2 已建立的八系统闭环从“结构正确”走向“真实教学有效”；
3. 是否能复用现有 Canonical Design / Spec，而不是制造第二套架构；
4. 是否能形成一条可验证的新的 vertical slice；
5. 是否存在足够证据支撑设计；若不确定性高，是否值得专项 Deep Research；
6. 是否需要真实长期数据才能证明收益；若需要，则不得过早上复杂模型。

## 2. v0.2 已冻结能力

v0.2 已建立并冻结：

```text
Material / SourceSpan
→ LearningGoal / LearningActivity
→ TeachingAction contract
→ EvidenceBundle
→ canonical Orchestrator
→ deterministic AssessmentResult
→ LearnerEvidence
→ MasteryEstimate
→ ReviewSchedule
→ future LearningPlan integration
→ restart / replay / recovery / security gate
```

同时已冻结八类系统的职责、状态所有权、依赖方向与 baseline 演进顺序。

因此 v0.3 禁止以“更先进”为理由重新讨论：

- AssessmentResult 与 MasteryEstimate 是否分离；
- LearningPlan 与 TeachingAction 是否分离；
- ReviewSchedule 与 LearnerState 是否分离；
- Retrieval 是否拥有教学策略；
- LLM/Agent 是否拥有业务状态；
- 是否直接使用 RL / 多 Agent / Deep KT 作为 canonical baseline。

这些属于已冻结架构，不是新的研究问题。

## 3. 当前最重要的结构性缺口

### G-01 — SYS05 Teaching Policy 仍主要停留在合同层

设计与 Spec 已完整规定 SYS05：

```text
LearnerState + AssessmentResult + LearningActivity + Review context
→ hard constraints
→ strategy state machine
→ candidate generation
→ weighted scoring
→ deterministic tie-break
→ TeachingAction
```

但当前 `apps/backend/app/domains/` 已建立 assessment、content_knowledge、learner_model、learning_planner、retrieval、review_scheduler，尚不存在独立 `teaching_policy` bounded context。

这意味着 v0.2 已经有 TeachingAction 合同与 canonical execution path，但“为什么这一刻应该讲解、追问、提示、练习或迁移”还没有形成完整的 SYS05 canonical decision engine。

这是当前最直接影响 Askora 教学智能差异化的缺口。

### G-02 — v0.2 主要证明系统闭环成立，尚未证明动态策略切换有效

当前闭环已经能区分：

- independent；
- assisted；
- answer-exposed；
- evidence weight；
- mastery projection；
- review / planning。

下一阶段应验证这些状态是否真的会改变 TeachingAction，而不是只被记录。

### G-03 — Error / misconception 信号还不足以驱动高质量 remediation

SYS04 目标是输出可审计的 error type 与 misconception evidence；SYS05 应根据这些信号决定补前置、换表征、增加支架还是继续独立练习。

v0.3 若要真正形成 Adaptive Teaching，需要把“评估结果 → 教学策略变化”做成可测试接口，但不需要一次性建设复杂开放题自动判分系统。

### G-04 — 产品化闭环仍需最小用户可见层

v0.2 的 release gate 主要验证内部领域闭环。v0.3 应让用户能够实际感知：

- 当前 LearningActivity；
- 系统为什么采用当前教学方式；
- 提示/答案暴露状态；
- 当前证据与掌握状态的保守解释；
- 下一步任务或复习来源。

这属于主闭环的产品化，不应独立发展成一套与领域状态无关的 UI truth。

## 5. 推荐 v0.3 主线

# Adaptive Teaching Loop

一句话目标：

> 在当前 LearningActivity 已确定的前提下，Askora 能根据 LearnerState、最近 AssessmentResult、错误类型、提示依赖、review context 与用户约束，以可解释、可回放的策略选择当前 TeachingAction，并根据新的行为证据持续升级、降级或退出支架。

核心闭环：

```text
LearningActivity
    ↓
TeachingContext snapshot
    ↓
SYS05 Teaching Policy
    ↓
TeachingAction
    ↓
SYS02 EvidenceBundle
    ↓
SYS08 execution
    ↓
Attempt / AssessmentResult
    ↓
SYS03 LearnerState update
    ↓
SYS05 re-evaluation
    ↓
next TeachingAction / activity completion
```

该切片首次让八类系统中的状态和证据真正影响“当前怎么教”。

## 6. 建议 In Scope

### 6.1 SYS05 canonical bounded context

建立实际 `teaching_policy` domain/application boundary，至少包含：

- TeachingContext；
- hard constraint evaluator；
- strategy stage mapper；
- candidate action generator；
- weighted scorer；
- deterministic selector；
- strategy/policy version；
- DecisionTrace；
- action outcome / reevaluation input。

### 6.2 最小策略族

v0.3 不追求全部策略成熟实现，优先形成覆盖学习阶段变化的最小集合：

```text
DIRECT_INSTRUCTION / WORKED_EXAMPLE
SOCRATIC_PROBING / GUIDED_PRACTICE
RETRIEVAL_PRACTICE
ERROR_REMEDIATION
TRANSFER_CHALLENGE
```

具体是否合并、拆分及转换条件需由专项研究决定后再写入 Canonical Design。

### 6.3 Scaffold fading

必须能验证：

```text
知识断层 / 连续失败 → 增加支架
提示后成功 → 不等价于独立掌握
连续独立成功 → 主动减少支架
答案暴露后成功 → 不用于高权 mastery，并需要后续独立验证
```

### 6.4 Assessment → Policy signal

只扩展支撑策略决策所必需的诊断信号：

- error type；
- independence；
- assessment confidence；
- misconception evidence/hypothesis reference；
- prior assistance history。

禁止为了 v0.3 同时建设通用开放题 Judge 平台。

### 6.5 Minimal user-visible learning state

前端至少能展示或解释：

- 当前任务；
- 当前教学动作；
- 为什么采用该动作的 reason codes 的用户友好表达；
- 提示/答案暴露状态；
- 当前状态是“证据不足/形成中/基本稳定”等，而不是伪精确概率；
- 完成当前 activity 后的下一步。

## 7. 明确 Out of Scope

v0.3 默认不进入：

- Contextual Bandit / Offline RL / Online RL；
- DKT/SAKT/SAINT 作为 canonical learner model；
- 复杂 IRT-CAT；
- 全学科开放题自动评分；
- 大型知识图谱或全请求 GraphRAG；
- 多 Agent 自主教学系统；
- 学校级多租户；
- 跨设备同步；
- 为追求目录整洁进行大爆炸 legacy 重命名；
- EPUB/音视频/网页等多内容源全面扩展（除非后续 scope 决策明确纳入）。

## 8. v0.3 前置治理 Gate

以下不是 v0.3 产品主线，但必须在新功能 EXEC 前或最早 EXEC 中完成：

### PG-01 — 清理 LD-001

`/users/profile` 改为 canonical read model / query adapter，删除 `API_NO_LEARNER_PERSISTENCE` legacy allowlist。

### PG-02 — 建立最小 CI

至少持久化：

```text

```

### PG-03 — Legacy responsibility 单调收敛

不要求 v0.3 全部物理搬迁，但任何新 Teaching Policy 功能不得继续写进通用 engine/orchestrator 形成新的职责混合。

## 9. 为什么不优先升级算法

当前系统是单用户优先，尚未积累足够的长期、多策略、题目校准数据。

因此：

- BKT → Deep KT：缺少证明复杂度值得的稳定数据；
- heuristic policy → Bandit/RL：缺少 action propensity、长期 outcome、可靠 OPE；
- simple planner → learned planner：缺少 activity duration / success history；
- default review model → 个体优化：缺少足够 review history。

v0.3 更正确的投资是：**把高质量日志、DecisionTrace、action outcome 和 delayed outcome 采集完整，为未来算法升级制造数据条件。**

## 10. v0.3 成功定义草案

v0.3 不以“策略数量”作为完成标准，而至少证明：

1. 同一个 LearningActivity 在不同 LearnerState / error / assistance context 下会产生不同且可解释的 TeachingAction；
2. hard constraints 永远优先于软评分；
3. TeachingAction 可 deterministic replay；
4. 模型/Agent 不能改变 policy decision；
5. 提示使用会影响后续支架与 mastery evidence；
6. 连续独立成功能触发 scaffold fading；
7. 连续失败或明确 misconception evidence 能触发 remediation，而不是机械重复；
8. 策略变化可追踪到 input snapshot、policy version、reason code 与后续 outcome；
9. 用户能看到最小必要的教学状态和原因解释；
10. v0.2 冻结的状态所有权、replay、安全和引用不变量全部保持。
